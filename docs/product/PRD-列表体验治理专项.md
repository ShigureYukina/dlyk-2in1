## 一、专项背景

### 1.1 问题现象（立项输入）

系统运行两年、线索/客户/交易相关流水数据达 30 万级后，三类问题同时出现：

| # | 现象 | 业务感知 |
| --- | --- | --- |
| P-1 | 列表翻页越翻越慢（压测前列表接口 P50 达 1000~1900ms） | 一线反馈"客户列表刷不出来"，投诉频发 |
| P-2 | 并发操作产生重复数据：同一条线索出现两个客户 | 跟进对象混乱，统计口径失真 |
| P-3 | 多实例部署下定时任务重复执行 | 重复跑批、重复通知 |

数据规模：压测环境按 `t_clue` / `t_customer` / `t_tran` 各 **35.6 万行**造数（`tools/db/01_gen_perf_data.sql`）。

### 1.2 根因定性（需求侧视角）

- **慢的根因**不是"某条 SQL 慢"，而是**同一个重活被每翻一页重复做一遍**：
  列表接口把"展示"和"统计"两件成本完全不同的事绑在一次请求里——每页都要执行一次
  7~9 表联查 + 一次对 35 万行的 COUNT。加机器、加索引、调连接池都只是把重复摊薄，去不掉重复。
- **脏的根因**：两个线程同时通过了同一个"手机号未登记"判断，之后各自落库，全程无防重设计。

## 二、治理原则与度量口径

### 2.1 优先级方法：频率 × 影响 × 成本

治理项多、资源有限，按三因子排序，**先做高频高影响低成本的事**：

| 因子 | 问的问题 | 取值来源 |
| --- | --- | --- |
| 频率 | 这个操作每天发生多少次？ | 接口调用配比（列表/字典/活动类是高频入口） |
| 影响 | 慢/错影响谁，投诉来自哪里？ | 业务反馈与 SQL 耗时数据 |
| 成本 | 改动面、风险、验证代价 | 方案评估 |

### 2.2 度量口径先行

开工前先定口径，避免"优化完说不清优了多少"：

- **口径四要素**：同一份数据 / 同一台机器 / 同一轮 / 同一口径。
- **指标分层**（两层不混用）：
  - *延迟层*：接口 P50 / P95 / P99（Locust CSV 导出）——索引与分页改造改善这一层；
  - *次数层*：每千次业务请求的 DB 查询量（MySQL `Com_select` 窗口增量归一化）——只有缓存能改善这一层。
- **归一化纪律**：对比组请求数不同时必须归一化；清缓存类请求不访问数据库，必须从分母剔除。

## 四、需求详情

### R1 联表 COUNT 改单表统计（P0）

- **问题**：列表 SQL 带 7~9 个 LEFT JOIN，分页组件对联查 SQL 自动生成的 count 耗时 505.8ms（线索）/ 977.8ms（客户）。
- **产品规则**：
  - 列表 total 必须与数据库直连统计**完全一致**（等价性是硬要求：实测线索 356,333 / 客户 356,344，与直连统计一致）；
  - 等价性前提写进验收：所有 LEFT JOIN 挂在被驱动表主键上、至多匹配一行，才允许改单表统计；
  - **带筛选条件的交易列表保留联查 count**——筛选条件可能落在被关联表上，单表统计会算错 total。正确性优先于性能。
- **验收**：单条 count 线索 40.2ms / 客户 27.9ms；total 数值与改前逐条一致。

### R2 列表 total 短 TTL 缓存（P0）

- **问题**：单表 COUNT 单条只要 40ms，"看起来无足轻重"，但每页都执行、且在 35.6 万行上扫描，
  50 并发下与分页查询争抢缓冲池和 CPU——**"单条 SQL 快"不等于"这个查询模式可以每页都打一次"**。
- **产品规则**：
  - **只缓 total、不缓结果集**：列表数据必须实时，total 允许 ≤10 秒延迟（与业务确认可接受）；
  - 缓存 key 固定（不按筛选条件组合膨胀），TTL 10 秒；
  - 必须带旁路开关（`LIST_TOTAL_CACHE_ENABLED`），支持灰度与对照实验；
  - 自埋点命中率指标，可观测可复盘。
- **验收**：命中率 98.8%；列表 P50 250→19ms（开关 A/B 同轮对照，降幅 92%）。

### R3 并发防重双层设计（P0）

- **问题**：并发提交同一线索时产生重复客户数据（P-2）。
- **产品规则**（详见线索 PRD F4）：应用层幂等（30s 窗口）+ 分布式锁串行化 + 库层条件唯一索引兜底；
  转换动作单事务完成，不允许部分成功；**手机号查重必须实时、禁止缓存**。
- **验收**：20 线程并发提交同一线索，零重复。

### R4 深分页游标化（P1）

- **问题**：偏移分页扫描行数随页码线性增长，深页 P50 720ms 且继续恶化。
- **产品规则**：提供游标分页通道（`/api/clues/cursor`），扫描行数恒为 limit、与页码无关；
  常规跳页保留偏移分页，两种通道并存按场景选择。
- **验收**：同一轮压测内对照，游标 P50 16ms vs 深页 720ms，且游标不随页码恶化。

### R5 热点接口缓存（P1）

- **问题**：活动列表、字典值是前端每次渲染页面必调的高频小接口，反复打库。
- **产品规则**：字典与活动数据允许短 TTL 缓存；缓存开关化。
- **验收**：缓存开启后这两个接口 DB 查询为 0（完全拦截）。

### R6 调度迁移 XXL-Job（P2）

- **问题**：`@Scheduled` 在多实例下重复执行（P-3）。
- **产品规则**：调度迁至 XXL-Job 分片广播，失败重试与告警在调度平台侧配置；本应用关闭内置调度（`XXL_JOB_ENABLED=false`）。
- **验收**：多实例下同一任务单次执行。

## 五、试点与灰度

### 5.1 试点设计

缓存方案涉及"数据延迟"这一产品取舍，**不直接全量推开**：

1. **缩小试点**：先只在列表 total 缓存上做（影响面最小、开关可旁路）；
2. **以指标对比推动落地**：用旁路开关做 A/B 两轮同配置压测（请求配比核对一致），拿命中率、耗时、DB 查询量三组数字决策；
3. **全量推开**：指标达标后开启为默认配置，开关保留用于应急回退。

### 5.2 对照实验的两个坑（方法论记录）

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| "无缓存"场景靠每请求前清缓存模拟 | 清缓存请求混入分母 → 得出"有缓存反而更费 DB"的错误结论 | 统一按业务请求归一化，剔除清缓存请求 |
| Spring 缓存 clear 默认走 KEYS 扫全键空间 | 上万次 KEYS 把"无缓存"组所有接口延迟抬高，跨模式比延迟不成立 | 延迟对比改用**旁路开关 + 重启**构造干净对照 |

### 5.3 明确不做：列表结果集缓存

- **代价**：列表页出现秒级数据延迟，且缓存键需按"页码 + 筛选条件"构造、数量随组合膨胀。
- **判断**：列表页是业务员做跟进决策的入口，秒级脏数据会直接影响判断——**这是产品决策而非技术决策**，
  本轮不擅自改动，按实测值如实表述。
- 这是本专项"DB 查询量降 70%"目标**未达成**（实测约 50%）的直接原因，记录在案。

## 六、效果验证（同口径对照）

### 6.1 结果总表

| 结论 | 数据 | 口径 |
| --- | --- | --- |
| 全局 DB 查询量下降约 **50%** | 每千业务请求 1,203 → 602 | bypass vs cached 两轮，归一化对比 |
| 列表接口 P50 **250 → 19ms**（降 92%） | total 缓存开关 A/B | 同为 cached 模式，唯一差别是该开关 |
| total 缓存命中率 **98.8%** | 自埋点指标 | 全量开启后 |
| 深分页 vs 游标 **720 → 16ms** | 同一轮压测对照 | 45 倍差距，游标不随页码恶化 |
| 热点接口 DB 查询 **完全拦截** | 活动列表 / 字典值 → 0 | 缓存开启后 |
| 并发防重 **零重复** | 20 线程并发用例 | 应用层 + 唯一索引双层 |

### 6.2 三组数字的口径边界（防混用）

| 数字 | 它是什么 | 它不是什么 |
| --- | --- | --- |
| 720→16ms | **深分页游标线**：同一轮内游标 vs 偏移深页的对比 | 不是全量列表接口的平均改善 |
| 250→19ms（92%） | **total 缓存线**：开关 A/B 的同模式对照 | 与游标改造无关，是两层不同的治理 |
| 1203→602（-50%） | **全局次数线**：全部治理叠加后的 DB 查询量 | 不含未达成部分；目标是 70%，实测约 50% |

50% 由缓存类治理贡献（热点接口约 20% + total 缓存单独 37%，乘法叠加）；索引与游标改的是单条 SQL 耗时，体现在延迟层而非次数层。

### 6.3 业务结果

治理上线后，列表卡顿相关投诉未再出现；并发重复数据经并发用例与对账观察均未复现。

## 七、复盘与遗留

| # | 结论 |
| --- | --- |
| 1 | **目标 70% 未达成，实测约 50%**——剩余部分只能靠缓存结果集，触碰"列表实时性"产品红线，本轮不做。把目标当结果是治理复盘的大忌，未达成记录在案。 |
| 2 | 优先级判断被验证：P0 三项（R1/R2/R3）以最低成本覆盖了最高频的痛点，投诉消失主要由这三项贡献。 |
